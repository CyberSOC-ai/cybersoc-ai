# ADR-001: Vector database

- Status: Proposed
- Date: 2026-10-29
- Author: Soulaiman (S2-T02, issue #17)
- Assigned reviewer: Ahmed; review and team acceptance pending
- CDC reference: §23

## Context

S2-T02 needs persistent, separate knowledge and SOC-history collections, source/
snapshot filters and evidence provenance. S2-T03 will measure retrieval quality;
S2-T04/S2-T05 will consume retrieval results. This decision does not implement
those tasks or certify retrieval quality.

The fresh local S2-T01 replay contains 164,793 records: 164,758 knowledge and 35
SOC excerpts/observations. It is development-only, with no frozen test split.
This replay is different from Ahmed's original acquisition. Its records SHA-256
is `7f954c3d7ad02c233d10ffca657d80708dea71350bf107a02e161d317af9a6a5`.
Actual point counts depend on later chunking and documented eligibility decisions.

The local machine has a Ryzen 5 5625U (6 cores/12 logical processors), about
13.84 GiB usable RAM and a Docker Linux VM with 6.69 GiB. Use CPU embeddings.
Long playbooks and flattened source whitespace require tokenizer-aware splitting;
character counts cannot establish that a document fits an encoder.

## Options considered

| Option | Assessment for this task |
|---|---|
| Qdrant server in local Docker | Selected: collections, typed payload filters/indexes and persistence support the required provenance boundary. Existing Docker workflow can host it. Adds a service and volume lifecycle. |
| Qdrant Python local mode | Convenient for small fixtures, but upstream describes it as small-scale and warns above 20,000 points. Do not use it as the full-corpus backend or treat its tests as server validation. |
| FAISS plus a separate metadata store | Useful vector-search library; we would also own metadata persistence, filter/ID mapping and consistency across stores. More application machinery for this task. |
| Chroma | Viable alternative with persistence and metadata filters. Qdrant is selected for explicit payload-index and storage controls, not because Chroma was benchmarked and found slower. |

Embedding candidates are English models appropriate to the current source text:

| Model | Documented properties | Decision |
|---|---|---|
| `BAAI/bge-small-en-v1.5` | 384 dimensions, 512-token maximum; CLS pooling and normalization; MIT | Select as initial passage-retrieval encoder. |
| `intfloat/e5-small-v2` | 384 dimensions, 512 tokens; query/passage prefixes; MIT | Credible alternative for a later controlled comparison. |
| `sentence-transformers/all-MiniLM-L6-v2` | 384 dimensions, default 256-wordpiece truncation; Apache-2.0 | Shorter default passage budget than the selected model. |

No local speed or relevance comparison was run. These are design choices, not a
claim that BGE or Qdrant is the best-performing option for cybersecurity.

## Proposed decision

Use the versioned [selection record](../../rag/vector/configs/selection-v1.json).
It is a design record, not a runnable build configuration. Runtime dependency
locking, chunking configuration and integration validation remain later steps.

- Pin BGE model **and tokenizer** to
  `5c38ec7c405ec4b44b94cc5a9bb96e735b38267a`. Use CPU float32, CLS pooling,
  L2 normalization, 384 output values, no quantization and initial batch size 16.
  Use Sentence Transformers with remote code disabled. Lock its compatible CPU
  dependency environment before inference; do not assume the native Python 3.14
  environment is supported. Target the existing Python 3.12 Linux workflow.
- Keep document prefix empty. Prepend the publisher's short-query retrieval
  instruction to queries, exactly as saved in the selection record. Include
  prefixes, titles and special tokens in the 512-token budget. Reject oversized
  queries with an explicit error and split oversized documents before encoding;
  never silently truncate evidence. The public 4,000-character query limit alone
  does not guarantee fit. Later API integration must expose that validation.
- Use Qdrant **v1.20.0**, Linux/amd64, pinned by image digest. Communicate through
  its REST API with the project's existing HTTP client. Keep embeddings explicit;
  do not configure a database-side model or hosted inference provider.
- Persist `/qdrant/storage` in a Docker named volume, avoiding the Windows/
  OneDrive bind mount for live database files. Publish REST on `127.0.0.1:6333`
  only; no public listener or cloud service is part of this local design.
- Create `knowledge_<build_id>` and `soc_history_<build_id>`, each with 384-value
  float32 vectors and cosine similarity. A build ID must resolve to an immutable
  manifest covering corpus, configuration, model/tokenizer artifacts and code.
  Refuse incompatible reuse. Never overwrite a prior build silently.
- Start with cold vector/payload storage, cached HNSW, `m=16`,
  `ef_construct=100`, one shard and one replica. These storage terms are Qdrant
  v1.20 API fields. Start searches with `hnsw_ef=128`; retain exact search for
  correctness comparisons. No quantization or relevance score cutoff initially.
  A cosine score is a ranking signal, not an incident probability.
- Index source, snapshot and selected provenance/eligibility filter fields before
  ingesting points. Preserve all required lineage; put only needed fields in
  payload indexes. Apply filters during retrieval, not just after taking top K.
  Internal filters do not introduce new public API fields.

Embedding text excludes evaluation labels and administrative split/group/path
metadata. Distinct CVE records retain separate identities even when descriptions
match. Preserve enrichment provenance; primary-description embeddings do not
replace exact CVE/KEV lookup in the ingestion `facts.sqlite` store. Returned evidence
must be explicitly projected into the closed v1 contract. The request source enum
still needs alignment with existing `detection_rule`/`playbook` evidence sources.

## Consequences

At one vector per input record, raw float32 vectors would occupy
`164793 * 384 * 4 = 253122048` bytes (about 241.4 MiB). This is an illustrative
vector-only estimate, not a measured index size or an upper bound: chunks, payload,
HNSW, WAL, temporary files and the model add storage/memory costs. Model weights
alone are 133,466,304 bytes according to the publisher's manifest. Runtime memory
is larger; initial batching must be checked with a real small build.

The local disk had about 22.8 GiB free at inspection, which is a transient reading.
Measure remaining disk and peak process/container memory before full indexing.
Record resolved server settings, environment locks, model artifact hashes,
configuration digest and timings in the build manifest. Snapshot/reload verification
is required; a Docker volume surviving container removal is not itself a backup.

Changing model, tokenizer, embedding projection or chunking requires a new build.
Floating-point and approximate-search results need not be byte-identical across
machines; use tolerances and deterministic tie handling. English/general-domain
embedding quality on commands, IDs and SOC events remains unmeasured. Preserve
source notices; this decision does not resolve source redistribution restrictions.

### Step 5 follow-up (2026-10-29)

The [chunker](../../rag/vector/README.md) now implements an initial 384-token
passage budget (including headers and special tokens), up to 48 tokens of overlap
and the 16,000-character evidence bound. The actual tokenizer JSON was acquired at
the selected revision and SHA-256 verified; no model weights were acquired.
Tokenizer-only dependencies are pinned. Embedding inference dependencies remain
pending. A real preview selected 17 records across six source types and produced
36 passages; replay matched chunk/decision bytes. This establishes chunking
behavior on the sample, not relevance or full-index performance. Source/split
eligibility, provenance, quality decisions and offsets are preserved in its
manifest and output. The filter-enum alignment remains for later integration.

### Step 6 follow-up (2026-10-29)

Added the [optional CPU environment](../../requirements-embeddings.txt), pinned
model acquisition and embedding/query adapters. Actual model weights and all ten
supporting files passed their recorded integrity checks. Local-only inference
with networking disabled encoded 36 preview passages into normalized float32
384-dimensional vectors. Replay reproduced vector bytes; batch/single and direct
CLS-pooling comparisons agreed within `1e-5`. Oversized inputs and mismatched
saved token counts were rejected. The saved chunk manifest/policy restrictions
propagate into the embedding manifest. Full corpus encoding, Qdrant deployment
and retrieval-quality evaluation remain future work; this ADR remains Proposed.

### Step 7 follow-up (2026-10-29)

The opt-in Compose service now runs the pinned Qdrant image on loopback REST with
the named volume `cybersoc-s2t02-qdrant`. Added a REST storage adapter and verified
artifact loader. The real preview loaded 33 knowledge and three SOC points into
separate versioned collections; all stored vectors, payloads, resolved settings
and typed payload indexes were checked. Recreating the container preserved those
points and indexes. Forty-four filter-value checks, negative/boundary checks and
filtered stored-vector queries passed before and after recreation. The same build
was refused on reload. No prior collection is overwritten or deleted by the loader.

Collections below the default threshold use full scans (`indexed_vectors_count=0`
in this preview); full HNSW scale/performance, full-corpus loading, query/evidence
integration and snapshot recovery remain unverified. Failed loads retain their
new collections for inspection and do not publish a completed receipt. Consumers
must require a receipt for a complete collection pair. ADR status remains Proposed.

### Step 8 follow-up (2026-10-29)

Added the query-to-evidence adapter with verified receipt/model identity, startup
point readback, per-request eligibility/state checks and filter-before-top-K
queries. Both collection candidate sets merge by raw cosine score into a bounded
result. Payload/vector fingerprints, score checks and explicit projection protect
the closed evidence boundary. The local draft request filter now names the two
existing Sigma/playbook evidence sources. Public response fields are unchanged.

Real exact-query checks covered SOC, playbook, Sigma and combined filters,
no-match results, token overflow, repeated queries and reader reconstruction from
persisted artifacts. The LSASS example cited the selected LSASS playbook. No
generation pipeline, API route, full-corpus performance or relevance metrics are
claimed. ADR remains Proposed for review.

### Final local validation and scope (2026-10-29)

The reviewed local development build covers 340 records and 406 real CPU-generated
vectors, with separate 369-point knowledge and 37-point SOC collections. Selection
and preview restrictions are explicit. All 35 prepared SOC records and the selected
Sigma/playbook documents are represented; knowledge references are a bounded subset.
The loader validates every stored vector/payload and preserves current eligibility.

Complete chunking of the acquired corpus produced 174,883 passages. Full-corpus
encoding, GPU execution and ANN-scale performance are additional work, not explicit
issue #17 acceptance requirements. Their absence is recorded as a coverage/scale
limitation for review. External-compute handoff artifacts and code were removed at
the user's request. The working CPU pipeline and original source artifacts remain.
ADR acceptance stays with peer review; status remains Proposed.

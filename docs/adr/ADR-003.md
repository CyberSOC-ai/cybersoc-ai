# ADR-003: Neo4j schema

- Status: Proposed — user local tests passed; integrity rerun, CI and review pending
- Date: 2026-11-06
- Participants: Achraf (owner), Ahmed (assigned reviewer; review pending)
- CDC reference: §3.1, §14, §17 Sprint 3, §23
- Issue: [S3-T01 #24](https://github.com/CyberSOC-ai/cybersoc-ai/issues/24)

## Context

S3-T02 needs a stable graph contract compatible with normalized ingestion records
and existing incident/evidence contracts. These inputs include scoped SOC entities,
ATT&CK techniques/relationships, CVE and source provenance. The current ATT&CK
adapter does not normalize malware objects; incident entities do not expose roles.

## Options considered

1. A generic Entity node and untyped relationships: flexible, but weak validation
   and ambiguous downstream queries.
2. An RDF/OWL ontology: expressive, but introduces a new representation and tooling
   beyond the planned Neo4j property graph.
3. Typed Neo4j business nodes, allowlisted directed relationships and versioned
   source references: selected proposal; fits existing JSON Schema and unittest.

## Proposed decision

Use [ontology v1](../../knowledge-graph/README.md): User, Host, IPAddress, Alert,
Vulnerability, Malware, AttackTechnique, ThreatIndicator, plus technical SourceRecord.
Alert corresponds to one normalized incident. All nodes use deterministic scoped
SHA-256 identities; relations identify endpoints and the supporting record version.
Preserve source/snapshot/content identity and allow parallel source assertions.
Validate self-contained batches offline with closed Draft 2020-12 schemas and
Python semantic checks. Existing backend contracts remain unchanged.

Provide idempotent node uniqueness constraints targeting Neo4j 5.x Community syntax;
an exact runtime version and edition must be recorded during database verification.
The validator checks mandatory fields and endpoint types independently of Neo4j.
Do not infer host/IP ownership, vulnerabilities or ATT&CK mappings from co-occurrence.
Defer CWE Weakness nodes and extra incident entity types; preserve source records
and report exclusions rather than silently discarding them. Malware population
requires an approved upstream source or adapter extension in S3-T02.

## Consequences

- ETL receives explicit shapes, identity rules, source mappings and rejection rules.
- Source references preserve multiple versions; retrieval must select an explicit
  release's source allowlist. Resolve historical display content from source records.
- Small self-contained batches repeat shared nodes; ETL must union provenance on
  stable keys and quarantine conflicting assertions. Partial-reference batches
  and automatic alias merges are outside v1.
- Required fields and relationship semantics are application validations; database
  uniqueness alone does not enforce them. No arbitrary STIX pattern interpretation.
- S3-T02 must enforce source hashes, split/run/group eligibility and source rights.
  S3-T03 performs population/database validation; S3-T04 implements evidence output.

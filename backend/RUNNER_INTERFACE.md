## Interface and ownership

The application factory accepts a trusted, process-local `BaselineRunner` object. The default is **no runner**: investigation of an existing incident returns HTTP 503 with `dependency_unavailable`, never a synthetic successful answer. Test runners live only in automated tests. No request can select/import code, choose a model path or configure a runner.

The agreed synchronous Python protocol is `run(request: RunnerRequest) -> dict`. `RunnerRequest` contains a detached validated incident, backend-issued `investigation_id` and `trace_id`, and an absolute `deadline_monotonic` in seconds from `time.monotonic()`. Input mode is always `no_rag`, one incident per call. No labels, evaluator context or retrieval packet is supplied. The incident already contains `schema_version: 1.0.0`; its original identity, source severity and ingestion provenance must be retained. Raw-event references are inert data, not fetch instructions.

The runner also exposes `versions`: the five strings required by the existing trace contract (`model`, `prompt`, `dataset`, `configuration`, full lowercase 40-character `commit`). Use immutable/versioned references resolvable through the S0-T06 experiment manifest; `dataset: not_applicable` is permitted for an individual API request, with the applicability reason in its external manifest. Model/configuration selection, tokenizer/chat template, prompt construction and actual inference remain S1-T03 responsibilities. Validate this configuration at application construction; do not load models in health or request handlers.

Return a complete candidate [investigation result](contracts/v1/investigation-result.schema.json) with the supplied IDs, `mode: no_rag`, no retrieved evidence and only `proposed` recommendations. The backend checks the unchanged JSON Schema plus cross-record identities, action IDs and proposal status before storing or reporting success. Inference cannot approve or execute actions. Source alert severity is distinct from assessed `risk_level`. The backend persists the incident, result and baseline trace; the runner does not write the API database. Configuration is trusted deployment input; model output is always untrusted.

## Deadlines, errors and concurrency

Default API inference timeout: **30 seconds**; default concurrent calls: 1, per application process. The existing [S1-T03 composition helper](../ai/baseline/api_adapter.py), `compose_api(..., timeout_seconds=180)`, explicitly configures **180 seconds** for CPU integration (its current default). This supplies `Settings(..., inference_timeout=180, inference_concurrency=1)` without changing the backend default. Match the core/runtime generation budget to the chosen setting; the core honors the earlier of its own deadline and the API deadline. Phi CPU generation can exceed 30 seconds, but successful Phi-through-API inference is not established by the Qwen smoke. Timeout selection is trusted deployment configuration, never an HTTP/model parameter. There is no waiting queue: a saturated runner returns HTTP 503. The API runs blocking inference off the event loop. A timeout returns HTTP 504 and records a failed investigation. Python cannot safely kill an inference thread: its slot remains occupied until the call exits, and a late answer is discarded. Client cancellation similarly does not permit unbounded replacement calls. The real runner **must** honor the deadline, including bounded loading/network/generation, or use a separately supervised process/service for hard cancellation. One Uvicorn worker is the supported SQLite/laptop configuration; multiple processes would multiply concurrency limits.

Raise `RunnerUnavailable` for missing/unavailable model resources (503) or `RunnerTimeout` for an internal deadline (504). Unexpected exceptions and invalid candidate output become sanitized `invalid_output` (502); exception text and model output are never included in HTTP errors. A schema-valid candidate `status: error` is not success: allowed inference errors map to 503/504/502. Backend storage failures return sanitized 503 `audit_unavailable`; success requires durable result/trace storage. Every actual inference attempt has a backend-created investigation/trace identity. No automatic inference retries.

## Verified integration and support boundary

Soulaiman's [integration evidence](../ai/baseline/API_INTEGRATION.md) reports 103 tests passing in a Python 3.12 Linux container and one real Qwen request through an **in-process ASGI client**: 201 for new incident ingestion, 200 for an identical duplicate and 200 for a contract-valid No-RAG investigation, with matching result/trace persisted in SQLite. Error mappings were exercised with controlled generators, not induced real-model outages. The tested backend snapshot was `d1957f7a804fabb274dc6a771b4e6cbec4f45bac`; the final PR head `38e5fcaecead21e4cac46588af50ccb43f1dd299` merged newer main without changes to the backend files.

The merged [adapter](../ai/baseline/api_adapter.py) preserves backend-issued IDs and the monotonic deadline, returns the complete result, supplies five trace-version fields and maps timeout/unavailable exceptions. Model loading, policy selection and version-manifest creation remain trusted composition responsibilities. Thread deadlines remain cooperative; agreement does not create hard process cancellation.

Supported backend execution is **Linux, Docker/Linux containers or an appropriate Linux environment such as WSL2**. Native Windows Python is unsupported: both the default runtime path and SQLite ownership checks use POSIX `os.getuid()`/ownership semantics. Supplying a runtime directory alone does not fix Windows compatibility; do not bypass the checks. The recorded integration used a separate Linux runtime image with `libgomp1` for llama.cpp, not proof that the generic backend image supplies every model-runtime dependency.

This evidence is a scoped historical smoke, not an independently reproduced official benchmark: the runner was uncommitted at measurement time, the recorded project SHA identifies its base checkout, and detailed model artifacts remain local as explained in the source record. It does not verify a real-model Uvicorn TCP deployment/external client, Phi-through-API, live Wazuh ingestion, authentication, multi-client production deployment or response execution. No new model run is performed by this documentation follow-up. Those boundaries do not invalidate the agreed interface or add the full #15 pipeline to Issue #12's scope.
